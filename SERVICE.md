# Сервис рекомендаций

Установка зависимостей, настройка S3 и команды запуска приведены в `README.md`.
Запуск из подготовленного окружения:

```bash
python -m uvicorn recommendations_service:app --host 127.0.0.1 --port 8000
```

Сервис читает три файла из `data/recommendations/`:

| Файл | Обязательные столбцы |
| --- | --- |
| `recommendations.parquet` | `user_id`, `item_id`, `rank` |
| `top_popular.parquet` | `item_id`, `rank` |
| `similar.parquet` | `item_id_1`, `item_id_2`, `rank` |

Если файлов нет, при запуске они скачиваются из `recsys/recommendations/`
персонального S3-бакета через `storage.py`. Для этого нужно задать `S3_BUCKET`
и настроить доступ boto3 либо существующий аккаунт CS Browser, как описано
в README. Ключи в репозиторий добавлять не нужно. Локальный каталог можно
изменить через `RECOMMENDATIONS_DIR`, префикс в бакете — через
`S3_RECOMMENDATIONS_PREFIX`. Уже скачанные файлы повторно не загружаются.
Для обновления рекомендаций остановите сервис и замените локальные файлы.

## API

Параметры передаются в строке запроса. `user_id` и `item_id` — неотрицательные
целые числа, `k` — целое число от 1 до 100. Неверные параметры дают HTTP 422.

| Метод и путь | Параметры | Ответ |
| --- | --- | --- |
| `POST /recommendations` | `user_id`, `k=20` | `{"recs": [идентификаторы]}` |
| `POST /events` | `user_id`, `item_id` | `{"status": "ok"}` |
| `GET /events` | `user_id` | `{"events": [треки от нового к старому]}` |
| `DELETE /events` | `user_id` | `{"status": "ok"}` |
| `POST /similar_items` | `item_id`, `k=10` | `{"recs": [идентификаторы]}` |
| `GET /health` | — | `{"status": "healthy"}` |
| `GET /stats` | — | Счётчики обращений |

`POST /events` регистрирует новое прослушивание. Сервис хранит последние
20 разных треков каждого пользователя; повтор перемещает трек в начало.
`DELETE /events` очищает только временную онлайн-историю указанного
пользователя. Обучающие события и файлы рекомендаций не изменяются.
Неизвестный трек можно зарегистрировать, но до обновления `similar.parquet`
он не создаёт онлайн-кандидатов.

Онлайн-кандидаты строятся по соседям трёх последних треков, офлайн-кандидаты
берутся из готовой персональной подборки или популярных треков. Списки
чередуются, начиная с онлайн. Повторные треки и вся недавняя история
исключаются; недостающие места заполняются доступными кандидатами и
популярными треками. Формула весов и порядок смешивания описаны в README.
Без истории порядок персональной подборки сохраняется. Похожий трек не
рекомендуется сам себе; для трека без соседей возвращается пустой список.

Счётчики `personal`, `popular` и `online` увеличиваются, если соответствующий
источник дал хотя бы один трек в успешный ответ `/recommendations`.
Один смешанный ответ может увеличить несколько счётчиков.
`similar` учитывает внешние вызовы `/similar_items`, `events` — успешные
добавления событий, включая повторные прослушивания. `errors` учитывает
ошибки чтения рекомендаций. При такой ошибке сервис возвращает HTTP 503.

История хранится в памяти одного процесса и пропадает после перезапуска.
Для этой версии используется один worker. DuckDB читает Parquet с фильтром
по пользователю или треку, файлы целиком в pandas не загружаются.
Обращения к одному соединению выполняются под блокировкой; прототип
рассчитан на проверку сценариев, а не на большую параллельную нагрузку.

## Тестирование

Проверка настоящего HTTP-сервиса на рассчитанных файлах:

```bash
python test_service.py --live --url http://127.0.0.1:8000 --data-dir data/recommendations --log test_service.log --output service_test_results.json
```

Скрипт проверяет пользователя без персональных рекомендаций, пользователя
с персональными рекомендациями без онлайн-истории и того же пользователя
после новых событий. Ожидаемые кандидаты читаются из реальных Parquet-файлов.
Проверяются изменения выдачи, присутствие двух источников, исключение
недавно прослушанных треков, ограничения API и счётчики.
Тест очищает временную историю выбранных тестовых пользователей перед
проверкой и после неё, поэтому его следует запускать на отдельном локальном
экземпляре сервиса.

Читаемый вывод сохраняется в `test_service.log`, ответы и результаты проверок —
в `service_test_results.json`. Успешный код завершения — `0`, при ошибке — `1`.

Проверки на искусственных данных без запущенного сервера и S3:

```bash
python -m unittest test_service -v
```

Они дополнительно проверяют точный порядок смешивания, повторные события,
ограничение истории, удаление дубликатов и неполные списки кандидатов.
Для совместимости `TestClient` используется `httpx==0.27.2` из зависимостей.
